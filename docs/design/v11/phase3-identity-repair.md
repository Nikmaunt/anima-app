# Задача 3 — ремонт идентичности, и почему он трогает не всё

Прогон v1.1c, 2026-08-01.

---

## 1. Расхождение, из-за которого задача исполнена не буквально

Задача формулирует инвариант так:

> concept = f(seed), seed = f(ANDROID_ID). Отсюда доказуемые признаки порчи:
> — сохранённый концепт не равен вычисленному из сохранённого сида; …

**До этого прогона функции `f` не существовало** (Фаза 0, §4). Облик выбирался
пальцем: галерея восьми тел при вылуплении и один тап в Настройках. Значит:

- признак порчи №1 сегодня неприменим к уже существующим душам;
- если ввести `f` этим прогоном и применить признак ко всем, то **7 душ из 8
  окажутся «испорченными»** — включая единственную прожитую, ту самую, которую
  промпт требует не переписывать деструктивно;
- при этом их облик не испорчен. Он **выбран человеком** сборкой, которая
  выбор предлагала. Стереть его «ради защиты» — это и есть та потеря, от
  которой задача защищает.

Отдельно: хендофф v1.1 содержит противоположное указание владельца дословно —
«Миграция: если в состоянии сохранён облик, отличный от сидового, **оставить как
есть, не переписывать**» (`docs/handoff-v11.md:200`). То есть два указания
владельца противоречат друг другу, и одно из них — про души, которых на момент
его написания ещё не существовало.

### Что сделано вместо

Введена **эпоха идентичности** (`IdentityOrigin`, `core/model`), одна строка в
`meta`:

| Эпоха | Кто пишет | Ремонтируется? |
|---|---|---|
| `ASSIGNED` | вылупление сборкой, которая выводит тело из сида (v1.1c+) | **да** |
| `TRANSFERRED` | импорт файла души | нет — тело принадлежит прежнему телефону |
| `CHOSEN` | **отсутствие строки**, то есть любая душа старше этого коммита | нет — тело выбрано человеком |

Для `ASSIGNED` инвариант `concept == assignedTo(seed)` держится **по
построению**: концепт вычисляется, а не спрашивается. Значит расхождение там —
настоящая порча, и сид авторитетнее, потому что он выведен из телефона.

Оба исполненных указания — «чинить порчу» и «не переписывать чужой выбор» —
таким образом выполнены одновременно, и признак порчи №1 работает ровно там,
где он доказуем.

**Открытый вопрос владельцу** — в отчёте, раздел 5.

## 2. Что чинится

`core/data/.../identity/IdentityRepair.kt`, вызывается из `AnimaApp.onCreate`
после прогрева хранилища, до первого чтения любым экраном.

| Порча | Почему доказуема | Что делает |
|---|---|---|
| строка сида = `0` | ни один `deviceSeed()` не может вернуть 0; это дефолт, записанный сломанным путём | перечитать сид с устройства |
| строки сида нет, а тело есть | тело не может существовать без числа, из которого оно выведено | перечитать сид |
| `concept != assignedTo(seed)` при `ASSIGNED` | концепт вычисляется при вылуплении | пересчитать из сида |
| строка тела нечитаема (`fromWire → null`) при живом сиде | облик из будущей версии или повреждённая строка | пересчитать из сида |

## 3. Что не трогается ни при каких условиях

Дневник тела, воспоминания (`soul_facts`), капсулы времени, чат, **дата
вылупления**, имя, счётчики. Идентичность — это четыре строки в `meta`;
прожитое — всё остальное, и оно не выводимо ни из чего, значит не
ремонтируемо.

Проверено не декларацией, а тестом: **каждый** тест `IdentityRepairTest`
сначала «проживает жизнь» (три записи дневника, два воспоминания, дата,
имя) и после ремонта сверяет их поштучно.

## 4. Резервная копия — путь, который можно назвать владельцу

```
/data/data/app.anima/files/identity-backup/identity-<миллисекунды>.json
```

Читаемый JSON с значениями **до** ремонта: имя, тело, сид, дата вылупления,
эпоха. Пишется до единой записи в БД. Если ремонт не нужен, каталог не
создаётся вовсе (тоже под тестом).

## 5. Локальная запись о ремонте

```
/data/data/app.anima/files/crash/identity-repair.txt
```

Дописывается, а не перезаписывается. **Не** `last-crash.txt`: тот файл
`AnimaApp` перетирает целиком при следующем падении и подписан на экране как
«последнее падение». Оба видны в Настройки → журнал падений.
Никакой телеметрии: у приложения нет сети вне двух модулей, и это не они.

## 6. Экспорт — четыре пути наружу (задача 3.5)

| Путь | Состояние | Чем закрыт |
|---|---|---|
| JSON-payload | отказывается (`NoBodyToExport`) | `SoulBackupIdentityTest`, поведенческий тест |
| зашифрованная копия | тот же payload | там же |
| markdown | отказывается до записи файла | `NoDefaultBodyTest`, чтение исходника |
| **открытка PNG** | отказывается до `createBitmap` | там же |

Прошлая сессия нашла и **исправила** дефект открытки; этот прогон его
проверил и закрыл тестом, который падает, если отказ окажется **ниже** первой
записи в файл. Честная оговорка: два последних — проверки текста исходника, а
не поведения: `SoulViewModel` требует `Context`, а в `feature/soul` нет ни
одного юнит-теста и нет Robolectric. Настоящая проверка этих двух — на
устройстве, первым пунктом в `docs/device-checklist-v11.md`.
