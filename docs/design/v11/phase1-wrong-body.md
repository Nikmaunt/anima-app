# Задача 1 — чужое тело: класс, а не случай

Прогон v1.1b, 2026-07-30. Ветка `main`.

Задание: «Первый кадр запуска показывает не то тело… Это отказ единственного
утверждения, на котором стоит продукт: тело назначено этому телефону.»

Порядок разделов — порядок, заданный владельцем: 1а (запись), 1б (диагностика
живых данных), 1в (весь класс), 1г (защита от возврата).

---

## 1а. SoulBackup — сначала

### Что установлено

Хендофф указывал на `SoulBackup.kt:132` как на место записи. **Это мёртвый
код.** `CreatureConcept.fromWire` была объявлена как
`fun fromWire(wire: String): CreatureConcept` — тип не-nullable, значит
`concept ?: SPIRIT_ORB` в строке 132 недостижим, и правка этой строки по букве
хендоффа не изменила бы ничего.

Запись происходила на уровень ниже — внутри `fromWire`:
`entries.firstOrNull { it.wire == wire } ?: SPIRIT_ORB`.

Мест записи оказалось **три**, а не два. Третье — `SoulViewModel.kt:170`,
markdown-экспорт, которого в списке хендоффа нет вовсе. Четвёртое найдено уже
в ходе 1в (открытка, см. ниже).

### Артефакт: тест, который сначала упал

`core/data/src/test/kotlin/app/anima/core/data/backup/SoulBackupIdentityTest.kt`
— 6 тестов. Написан до правки, утверждает то поведение, которое файл души
обязан иметь. На неисправленном дереве два из шести упали и **напечатали
доказательство**:

```
core/data:testDebugUnitTest --tests '*SoulBackupIdentityTest*'
tests=6 failures=2

--- FAILED: export refuses a soul with no body rather than inventing one
expected: null
but was : {"format":"anima-soul","version":2,"exportedAtMillis":1700000000000,
           "creature":{"name":"","concept":"spirit_orb","seed":0,
           "hatchedAtMillis":1700000000000},
           "facts":[],"journal":[],"timeCapsules":[]}

--- FAILED: an unknown body in a file is refused, not silently replaced
expected: null
but was : spirit_orb
```

Второе «but was» — это значение, прочитанное обратно **из строки
`creature_concept` таблицы `meta`**, то есть из долговременных данных.

Четыре теста, которые прошли и на неисправленном дереве, отвечают на остальные
вопросы задания:

| Вопрос задания | Тест | Ответ |
|---|---|---|
| попадает ли дефолт в шифрованную копию | `the encrypted copy carries exactly what the payload carries` | **Да.** Копия — это те же байты payload внутри `SoulBackupCodec`; кодовая фраза защищает файл от посторонних, а не душу от приложения |
| переносится ли на другое устройство при импорте | `what one device writes, the next device becomes` | **Да.** Экспорт из одной БД, импорт во вторую — вторая становится тем, что записала первая |
| попадает ли в markdown-экспорт | — | **Да**, но не тестом: подстановка стояла в `SoulViewModel.kt:170`, в модуле без юнит-тестов, и `SoulPort.export` пишет `concept.wire` прозой («A creature of the spirit orb kind.», `SoulPort.kt:23`). Держится грепом из 1г |

### Достижимость — честно

Два пути, и они очень разной тяжести. Это существенно, и в задании этого
различения нет.

**Путь A — экспорт без личности.** Достижим на уровне API,
**но через сегодняшний UI недостижим.** `identity.concept()` возвращает null
ровно тогда, когда строки `creature_concept` нет, то есть до вылупления. Экран
Души стоит за `prefs.onboardingDone()`, а флаг ставится **после**
`identity.hatch(...)` (`OnboardingViewModel.kt:66-71`), поэтому прерванный
онбординг просто начинается заново. Android Auto Backup выключен
(`allowBackup="false"`), значит подмены «prefs восстановились, БД нет» тоже не
будет; `fallbackToDestructiveMigration` в сборке БД нет
(`DataModule.kt:45-51`), значит и тихого пересоздания пустой БД нет.

Это заряженное ружьё, а не выстрел. Закрыто потому, что Фаза 4 собирается
добавить на этот экран вход «восстановить душу» (design-system-v11 §3 называет
его одним из двух законных случаев плашки), и такой вход делает путь A
достижимым.

**Путь B — неизвестный облик в файле.** Достижим **сейчас, без экзотики.**
Любой файл, называющий тело, которого нет в этой сборке — бэкап из более
поздней версии, повреждённый файл, отредактированный файл, — молча
перерождал существо как `SPIRIT_ORB` и записывал это в `meta`. Проверка
версии не помогает: `SoulBackup.VERSION = 2` описывает формат конверта, а
набор обликов может вырасти, не сдвинув номер формата.

Это и есть то, о чём говорит задание: «перерождение перенесёт чужое тело».

### Что сделано

- `CreatureConcept.fromWire` возвращает `CreatureConcept?`. Форма не новая —
  `JournalKind.fromWire` в том же пакете так работал всегда. Вызывающих было
  три: этот бэкап и два уже-nullable чтения в `IdentityRepository`.
- `exportPayload` читает личность **первой строкой** и бросает
  `SoulBackup.NoBodyToExport`, не дойдя до формирования файла.
- `importPayload` бросает `SoulBackup.UnknownBodyInFile` **до первой записи**.
- Markdown-экспорт не пишет файла вовсе, пока тело неизвестно.
- Два новых случая в закрытом множестве `BackupNotice` вместо переиспользования
  `ExportFailed`/`ImportFailed`: оба существующих говорят «с файлом что-то не
  так», а здесь с файлом всё в порядке. Ни один из новых не несёт detail —
  у второго detail был бы недоверенным текстом из файла (инвариант «д.4»).
  Строки во всех шести локалях.

## 1б. Диагностика уже существующих данных — ТОЛЬКО ЧТЕНИЕ

### Короткий ответ

**Команды adb, которая прочитает облик, не существует, и это не обход, а
устройство приложения.** Строка живёт в
`/data/data/app.anima/databases/soul.db`, база зашифрована SQLCipher, ключ —
AES из AndroidKeyStore (`core/data/.../crypto/SoulKeySource.kt:61,95`), то есть
неизвлекаемый по построению. `adb backup` тоже закрыт: `allowBackup="false"`.
`sqlite3` в шелле прочитает только шум.

Поэтому ниже — экранный способ. Ранжирован по риску для данных.

### Способ 1 (рекомендую): Душа → «поделиться душой» (markdown)

Экран Души → кнопка экспорта в markdown (не «сохранить душу» с кодовой фразой,
а именно текстовый файл). В файле будет одна строка вида:

```
A creature of the fox kit kind.
```

Это `concept.wire` с подчёркиваниями, заменёнными на пробелы
(`core/model/.../SoulPort.kt:23`) — то есть **буквально то, что лежит в
строке `creature_concept`**, без пересказа.

- Читается «fox kit» → в душе записан `fox_kit`, всё чисто.
- Читается «spirit orb» → записан `spirit_orb`, и тогда решение принимаете вы.

Что этот способ делает с данными: пишет один временный `.md` в собственный кэш
приложения (`cacheDir/exports/`), удалив предыдущие экспорты оттуда же, и
открывает системный «Поделиться». **Душу он не меняет.** Диалог можно закрыть;
`AnimaApp` вычищает этот каталог при следующем старте.

Работает на той сборке, которая у вас стоит сейчас. На новой сборке поведение
другое и тоже информативное: если строки нет, файл не создаётся вовсе, а
уведомление говорит «Тело ещё не назначено — переносить пока нечего.»

### Способ 2 (перекрёстная проверка, но осторожно)

Настройки → раздел «ТЕЛО»: сетка из восьми обликов, и в ней **подсвечен ровно
тот, который записан** — маркер выбора берёт сырое nullable-значение
(`SettingsScreen.kt`, `ConceptGallery(selected = state.concept)`), а не
подставленное. Если не подсвечен ни один — строки нет или значение неизвестно.

> ⚠️ **На этом экране один тап по любой плитке немедленно перезаписывает
> тело** — `onSelect = viewModel::switchConcept` → `identity.switchConcept`,
> без подтверждения и без отмены. Если пользуетесь этим способом — только
> смотреть, не касаться. Способ 1 безопаснее.

### Отдельно: ваша душа, скорее всего, не испорчена

Записывающих строку `creature_concept` в коде ровно три
(`grep -rn "switchConcept\|\.hatch("`):

1. `OnboardingViewModel.kt:69` — облик, который вы выбрали при вылуплении;
2. `SettingsScreen.kt:184` — тап по плитке в сетке «ТЕЛО»;
3. `SoulBackup.kt:155` — импорт файла души.

Ни один дефект из 1а не пишет в вашу душу сам по себе. Значит `spirit_orb`
может там оказаться только если вы (1) выбрали его при вылуплении,
(2) случайно тапнули по плитке в Настройках или (3) импортировали файл. Мигание
чужого тела при запуске, с которого началась эта задача, — дефект **чтения**:
начальное значение `HomeUiState`, а не то, что записано.

Проверить всё равно стоит — пункт (2) стоит один случайный тап.

## 1в. Класс целиком

### Сколько их было

Хендофф насчитал девять. Фактически:

| Категория | Было | Где |
|---|---|---|
| подстановка `?: SPIRIT_ORB` | **14** | см. `docs/design/v11/phase0-v11b-audit.md` §5.1 |
| дефолт поля состояния `= SPIRIT_ORB` | **6** | Home, BodyDiary, Rest, Wardrobe, Soul, Story |
| начальное значение потока | **1** | `SoulViewModel.kt:101` — `SPIRIT_ORB to 0L` |
| жёстко зашитый облик | **1** | `OnboardingScreen.kt:184` |
| дефолт сида | **вся параллельная серия** | `?: 0L` и `= 0L` рядом с `seed` |

Пять из четырнадцати подстановок хендофф не назвал, и среди них **обои**
(полноэкранная поверхность домашнего экрана) и **три места на экране Души**
(поверхность переноса, то есть платная часть).

### Разделение: чтение и запись

Задание требует разделить. Разделяю.

**Места ЗАПИСИ — четыре.** Дефолт уезжает в данные, которые нельзя
воспроизвести, и переносится на другой телефон:

| Место | Что писалось | Теперь |
|---|---|---|
| `SoulBackup.kt:55` (JSON payload) | `"concept":"spirit_orb","seed":0` в файл души | `NoBodyToExport`, файла нет |
| `SoulBackup.kt:129→155` (импорт) | `spirit_orb` в строку `meta` | `UnknownBodyInFile`, до первой записи |
| `SoulViewModel.kt:170` (markdown) | «A creature of the spirit orb kind» в файл, уходящий с телефона | файл не создаётся |
| `SoulViewModel.kt:229` (**открытка**) | PNG чужого тела через «Поделиться» | уведомление «тела ещё нет» |

Четвёртое — **новая находка этого прогона.** Открытка брала
`identityBits.value` через деструктуризацию, а начальным значением этого потока
был `SPIRIT_ORB to 0L`. То есть «поделиться открыткой» до завершения init-корутины
отрисовало бы и отправило наружу чужое существо. Нашлось только потому, что
снятие дефолта у `identityBits` сломало компиляцию именно здесь.

**Места ЧТЕНИЯ — остальные.** Дефолт портит кадры, а не данные. Тяжесть внутри
этой группы тоже разная, и она определяется не кодом, а тем, кто смотрит:

| Поверхность | Почему именно так | Теперь |
|---|---|---|
| **Обои** `AnimaWallpaperService.kt:126` | полный экран за иконками; подменённое тело здесь никто не станет считать багом | только фон, тела нет |
| **Виджет** `AnimaWidget.kt:45` | то же, рядом с иконками лаунчера | пустой, но нажимаемый — открыть приложение и увидеть, что не так; текста нет (инвариант «нечего читать») |
| **Home** `HomeViewModel.kt:76,761` | тот самый первый кадр запуска | пустой бокс того же размера, поэтому при появлении тела ничего не прыгает |
| **Душа** `SoulViewModel.kt:101,151` | рисовала `SPIRIT_ORB` на первых кадрах **при каждом открытии**, а не только при сбое | пусто |
| Rest, Дневник тела, «Я и Anima», Формы | тот же класс | пустой бокс/спейсер того же размера |
| Онбординг `:86` | недостижимая ветка (NAME доступен только после `onConceptConfirmed`) | убрана: недостижимое не должно выглядеть обработанным |
| Онбординг `:184` | «формless spirit» был буквально `SPIRIT_ORB` — из яйца человека, которому назначена лиса, вылуплялось другое существо | свет без признаков облика: то же свечение, что уже сочилось из трещин, раскрытое наружу |

### Сид — то же самое

`CreatureGenome.from(seed)` — это характер, темп мигания, размер. Сид `0L` —
чужая личность ровно в той же степени, в какой `SPIRIT_ORB` — чужое тело.

- Все `identity.seed() ?: 0L` сняты. Там, где сид нужен для выбора реплики из
  пула (утреннее приветствие, «доброй ночи», сон, «нора стала просторнее»),
  функция теперь **не говорит ничего**, вместо того чтобы говорить чужую строку.
- `RenderContext.seed` был `var seed: Long = 0L`. `pose` и `genome` в том же
  классе — `lateinit` именно затем, чтобы забытое присваивание падало;
  для `Long` это невыразимо, поэтому контракт выписан руками (флаг + `check`),
  без `Long?`, потому что этот класс переиспользуется каждый кадр под правилом
  zero-alloc.
- `OnboardingUiState.seed` потерял дефолт `0L` совсем: он всегда конструируется
  с настоящим сидом устройства, и дефолт означал только, что второй, будущий
  конструктор смог бы вылупить сид 0 молча.

### Найдено попутно и НЕ исправлено — вопрос владельцу

`OnboardingViewModel.deviceSeed()` (:79-92):

```kotlin
val id = runCatching { Settings.Secure.getString(..., ANDROID_ID) }
    .getOrNull() ?: "anima-fallback"
```

Телефон, у которого `ANDROID_ID` не читается, получает **фиксированную строку**,
то есть фиксированный сид, то есть **то же самое существо, что все остальные
такие телефоны**. Это тот же класс дефекта: дефолтная личность.

Не меняю, потому что выбор — продуктовый, а не технический:
`SecureRandom` даёт уникальность, но ломает свойство «переустановка возвращает
то же существо», которое даёт `ANDROID_ID`. Нужен ваш ответ.

### Также убрано

`ChatScreen.kt:60` содержал `remember { CreatureGenome.from(state.seed) }` с
комментарием, что это нужно для настройки голоса. Значение отбрасывалось,
а голос настраивается во view model. Nullable-сид выявил это как мёртвый код —
удалён, а не сделан null-безопасным.

## 1г. Защита от возврата

`app/src/test/kotlin/app/anima/NoDefaultBodyTest.kt` — 4 теста, **в обычном
контуре `check`**, не за флагом. Читает исходники как текст, по образцу
`ChatDemotionTest` и `NetworkIsolationTest`, потому что это утверждение о том,
чего в исходниках быть не должно.

| Тест | Что держит |
|---|---|
| `no production source falls back to a named body` | `?: <любой из восьми>` и `= CreatureConcept.<любой из восьми>` в `src/main` любого модуля |
| `no production source falls back to a default seed` | `?: 0L` рядом с `seed`, и `seed: Long = <число>` |
| `the Home state cannot name a body or a seed before it reads one` | `HomeUiState.concept`/`seed` остаются nullable — `stateIn` обязан получить начальное значение, и это значение и есть первый кадр каждого запуска |
| `the soul file refuses an unknown body instead of substituting one` | три ключевых строки в `SoulBackup` и nullable `fromWire` |

Перечислены восемь имён обликов, а не один `SPIRIT_ORB`: иначе правило
обходится выбором другого тела.

Исключения названы поимённо, а не шаблоном: восемь файлов-таблиц, которым
называть все восемь обликов — работа (сам enum, рендерер-роутер, `RigScale`,
`SignatureHue`, `VoiceCharacter`, `Personality`, галерея, превью), и отдельно
`CreaturePreviews.kt` для правила о сиде — `@Preview` не композится
приложением и существует ровно затем, чтобы разработчик посмотрел на все
восемь.

### Артефакт: греп кусается

Не «тест зелёный», а «тест падает, когда должен». Два доказательства.

**Первое, случайное.** На первом же прогоне тест упал на двух настоящих
нарушениях, которые я к тому моменту не заметил:

```
FAIL: no production source falls back to a default seed
core/creature/.../CreaturePreviews.kt:25: default seed —     seed: Long = 7L,
feature/onboarding/.../OnboardingViewModel.kt:26: default seed —     val seed: Long = 0L,
```

Первое стало названным исключением, второе — исправлением.

**Второе, намеренное.** В `RestViewModel` временно посажена регрессия
(`?: CreatureConcept.JELLY` и `?: 0L`), прогон, откат:

```
tests=4 failures=2
FAIL: no production source falls back to a named body
  feature/rest/.../RestViewModel.kt:68: fallback to a named body —
      concept = identity.concept() ?: CreatureConcept.JELLY,
FAIL: no production source falls back to a default seed
  feature/rest/.../RestViewModel.kt:69: default seed —
      seed = identity.seed() ?: 0L,
```

### Чего этот греп не поймает

Честно, чтобы никто не считал его сильнее, чем он есть: он ловит две текстовые
формы — элвис и присваивание. `CreatureConcept.entries.first()`,
`values()[0]`, вычисленный индекс или подстановка через отдельную функцию
пройдут мимо. Формы, которые существовали в этом дереве, закрыты; изобретательный
обход — нет.
