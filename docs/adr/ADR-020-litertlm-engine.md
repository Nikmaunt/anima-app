# ADR-020: Судьба рантайма — LiteRtLmMindEngine как аддитивная вторая реализация, CPU-only, флаг OFF

Дата: 2026-07-24 (v0.7). Статус: принято.
Исполняет «dual-runtime поэтапно» из ADR-016; ADR-016 не пересматривается.

## Контекст (research: docs/freshness-2026-07.md §A)

Гейт ADR-016 «добавить LiteRT-LM-движок, когда…» сработал по условию (в):
tasks-genai официально в **maintenance-only** (рекомендация Google —
мигрировать на LiteRT-LM), заморожен на 0.10.35 (2026-04-27), и для
кастомных .litertlm-конверсий (наш int4-конвейер tools/qwen-int4)
гарантий чтения в maintenance-режиме нет. LiteRT-LM 0.14.0 (2026-07-08):
Kotlin API «Stable» (0.x, semver не обещан), litertlm-android +
litertlm-jvm на Google Maven.

Одновременно GPU-бэкенд LiteRT-LM на Samsung сломан широким кластером
открытых issues (#2292 S24 Ultra: Engine.initialize() падает, автофолбэка
нет; #2114 Xclipse 960; #2611, #1864, #2211), CPU-бэкенд стабилен
(#2292, #1748: комьюнити int4 на CPU работает на Linux и Pixel 8).

## Решение

1. **LiteRtLmMindEngine** — вторая реализация за существующим
   `MindEngine`-интерфейсом в `:core:mind`. Реестр (ADR-017), форматный
   слой (PLAIN/CHATML, StreamTrimmer), бюджеты промптов — общие: движок
   получает всё из `MindModelSpec`, контур CLOUD→NANO→GEMMA/LOCAL→сон
   не знает, какой локальный движок под флагом.
2. **CPU-only, запрещено кодом**: `Backend.CPU()` — единственный
   создаваемый бэкенд; упоминания `Backend.GPU`/`NPU` в модуле ловит
   тест (`LiteRtLmCpuOnlyTest`), а не комментарий. Это ужесточение
   паттерна ADR-016 («try-GPU → catch → CPU»): пока жив Samsung-кластер
   issues, GPU не пробуем вовсе. Пересмотр — отдельным ADR при закрытии
   #2292/#2114.
3. **Фичефлаг в настройках разработчика (debug-сборки), default OFF**;
   tasks-genai остаётся дефолтным движком GEMMA-тира. Флаг меняет только
   реализацию локального движка, не тир-ладдер.
4. **Сетевой инвариант**: litertlm-android подключается только в
   `:core:mind`; NetworkIsolationTest получает allowlist-тест
   зависимостей `:core:mind` (по образцу listener/cloud-mind), бюджет
   смёрженных разрешений уже пинит любые манифест-сюрпризы транзитивов.
5. **JVM-смоук** (`tools/litertlm-smoke`, gradle-таск вне дефолтного
   CI, гейт `ANIMA_JVM_LLM_SMOKE=1`): litertlm-jvm 0.14.0 + CPU +
   наименьшая готовая модель litert-community
   (`gemma3-270m-it-q8.litertlm`, ~290 MiB, скачивается во временную
   директорию) — первый в истории проекта инференс, выполнимый без
   телефона; фиксирует работоспособность конкретной связки версий.

## Критерии смены дефолта (будущий прогон, не этот)

- S24-чеклист: LiteRtLmMindEngine на той же модели ≥ tasks-genai по
  качеству/скорости/памяти (пункт добавлен в manual-checklist v7);
- закрыт вопрос чтения наших int4-конверсий текущим рантаймом
  (смоук + устройство);
- нет незакрытых P0-issues CPU-бэкенда на arm64.

## Последствия

+ Уход с deprecated-рантайма подготовлен без риска для проверенного
  стека; переключение — один флаг.
+ Смоук на хосте дал проекту первый быстрый инференс-контур без S24.
− Двойная поверхность рантайма в :core:mind (два нативных стека в APK,
  +размер debug-сборки; release не растёт, пока флаг debug-only).
− 0.x-зависимость с недокументированными breaking-изменениями —
  каждый бамп litertlm сопровождать смоуком.
